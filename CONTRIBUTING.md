# Contributing

This file covers the documentation site in `docs/`. For the package itself, follow the usual
IBL review process.

## Building the site locally

The site is built and reviewed locally. There is no deploy workflow yet, so
`https://int-brain-lab.github.io/iblatlas/` does not resolve.

You need [Quarto](https://quarto.org/docs/get-started/) and a Python **3.10 or newer**
environment. `venv/` at the repository root is already gitignored:

```bash
uv venv --python 3.12 venv
uv pip install --python venv/bin/python -e . -r docs/requirements.txt
```

Note `uv venv` creates an environment without `pip`, so install through `uv pip` as above (or
create it with `uv venv --seed` if you want `pip` inside it).

Then, to build — with `venv/bin` on your `PATH`, or via `source venv/bin/activate`:

```bash
quartodoc build --config docs/_quarto.yml
quarto render docs/
```

Open `docs/_site/index.html`.

`quartodoc build` must run before `quarto render`: it generates everything under
`docs/reference/`, which is gitignored precisely because it is reproducible.

`griffe` is pinned `<2` in `docs/requirements.txt`. This is not optional — quartodoc 0.11.1
crashes against griffe 2.x with `TypeError: parse_numpy() got an unexpected keyword argument
'allow_section_blank_line'`.

## Adding a page

Pick the quadrant by what the reader is doing, not by subject matter:

| Quadrant | For | Directory |
|---|---|---|
| **Tutorial** | Learning the package for the first time, guided | `docs/tutorials/` |
| **How-To** | Accomplishing a specific task they already have | `docs/how-to/` |
| **Reference** | Looking up what a symbol does | generated — see below |
| **Explanation** | Understanding why something works as it does | `docs/explanation/` |

The commonest mistake is writing an explanation inside a how-to. If a paragraph starts
explaining *why*, it probably belongs in the Explanation quadrant with a link from the how-to.

Add the page to the `navbar` in `docs/_quarto.yml`, or nothing links to it.

## Adding to the API reference

`docs/reference/api/` is generated by `quartodoc`. **Do not hand-edit anything in it** — the
next build overwrites the whole directory, which is why it is gitignored.

`docs/reference/index.qmd` and `docs/reference/data-files.qmd` sit above it, are hand-written
and are committed. They survive a rebuild.

The documented API is the `contents:` list under `quartodoc.sections` in `docs/_quarto.yml`.
quartodoc has no auto-discovery, so a new public symbol appears in the reference only if you
add it there, or record why it is omitted in `docs/_exclusions.yml`.

`options: include_inherited: true` must stay set. Without it a subclass page shows only its own
members — `AllenAtlas` renders 5 instead of 18, losing everything inherited from `BrainAtlas`.

## Notebook pages and their figures

Quarto **does not execute** `.ipynb` files when rendering. It uses whatever outputs the
notebook already contains. So a notebook committed with its outputs stripped renders as code
with no figures.

To add or refresh figures, run the notebook yourself and commit it **with outputs**:

```bash
venv/bin/jupyter nbconvert --to notebook --execute --inplace docs/how-to/<page>.ipynb
```

This downloads atlas data — several gigabytes on a cold cache — so do it deliberately, on a
machine where the data is already cached.

Because nothing executes at build time, rendering the site downloads nothing.

## What is not checked automatically

This phase of the site has no CI. All of the following are manual:

- that the reference `contents:` list still matches the package's public symbols;
- that documented symbols actually have docstrings;
- that notebook outputs were produced against the current `iblatlas` version;
- that the prose is still true after a code change.

If you change a public API, update `docs/_quarto.yml` and any page that describes the old
behaviour in the same pull request. Automated checks for these are planned but not written.

## `examples/` is still here, and duplicates ten of these notebooks

Ten notebooks currently exist **twice**: in `examples/` and under `docs/`.

**The copies under `docs/` are the live ones.** They are what the site builds. Editing the
`examples/` copy changes nothing on the site.

This duplication is deliberate and temporary — the documentation site was built additively,
without moving or deleting anything, and a later cleanup pass removes `examples/`. Until then,
check you are editing the file under `docs/`.
